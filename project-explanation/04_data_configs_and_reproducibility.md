# Data, Configs, And Reproducibility

The benchmark is config-driven. A config file describes the experiment name, datasets, splits, graph representation, models, scenarios, seeds, metrics, and disclosures. The source code reads the config and uses it as the single source of truth. This is important because robustness benchmarks can become hard to reproduce if parameters are scattered across scripts. In this repo, the JSON config is where the experiment design lives.

The current main config is `configs/exp_yelpchi_v3.json`. It defines YelpChi as the dataset, one fixed split called `s0`, four models, five stress scenarios, two graph seeds, three training seeds, and three evaluation metrics. The fast config `configs/exp_yelpchi_v3_fast.json` keeps the scenario surface but reduces models and seeds for smoke testing. The full config `configs/exp_yelpchi_v3_full.json` uses denser severity curves and broader seed coverage. The older v1 and v2 configs remain frozen so historical runs can still be reproduced.

Configuration validation happens in `benchmark/config.py`. The validation layer checks that required top-level keys exist, that seed lists are valid, that scenario methods are known, that severity values are non-negative, and that v3 metadata such as `oracle_mode`, `graph_view_mode`, and `relation_filter` is well formed. This is not just defensive programming. It prevents invalid experiment definitions from producing misleading outputs.

The data loading path starts in `_make_source_graph()` in `benchmark/run.py`. That function calls `load_dgl_fraud_dataset()` from `benchmark/data.py`, which imports `dgl.data.fraud.FraudDataset` lazily and loads the configured dataset name, such as `yelp`. Lazy imports are used so lightweight commands and tests can run without immediately importing all deep learning dependencies.

After loading the DGL graph, the benchmark normalizes basic tensor types. `ensure_feature_dtype()` casts features to `float32`, and `ensure_label_dtype()` casts labels to integer labels with shape `(N,)`. This type normalization matters because research datasets and DGL loaders may expose tensors in slightly different shapes or dtypes. Model code is simpler and safer if the benchmark standardizes those tensors before downstream stages.

The split masks are generated by `ensure_masks()` in `benchmark/data.py`. It overwrites `train_mask`, `val_mask`, and `test_mask` using a deterministic stratified split. Stratification means each class is split separately, which helps preserve the class distribution in train, validation, and test subsets. This matters for fraud detection because the positive class is usually rare. A random non-stratified split could accidentally create a validation or test set with an unusual fraud rate.

The graph representation is controlled by `graph_representation.canonical_view` in the config. The current configs use a homogeneous canonical view, created with `dgl.to_homogeneous`. The source YelpChi graph can be relation-aware, but the benchmark evaluates all models on one shared view for comparability. In v3, some perturbations are generated on the source heterograph first and then converted back to the homogeneous evaluation graph. This gives relation-aware stress generation without forcing every downstream model to become heterograph-native.

The graph cache is organized by `benchmark/paths.py`. The clean graph is stored under a base path such as `graphs/base/yelpchi/s0/graph.bin`. Stressed variants are stored under paths such as `graphs/variants/yelpchi/s0/<scenario>/<severity>/seed_<graph_seed>/graph.bin`. Severity directory names are formatted with two decimals so the same severity value maps to a stable folder name.

Graph saving and loading are handled by `benchmark/cache.py`. A graph binary is saved with DGL's `save_graphs`, and a companion `meta.json` records metadata such as the experiment name, split, scenario, severity, graph seed, and scenario parameters. For no-op variants such as severity `0.0`, the benchmark can write a `graph_ref.json` that points back to the clean graph instead of duplicating a large graph binary. This saves space while keeping the ledger complete.

The graph stage writes `graph_variants.csv` as the variant ledger. Each row records the dataset, split, graph seed, scenario, severity, whether oracle labels were used, whether the scenario was actually applied, graph paths, and basic graph statistics such as node count, edge count, degree summaries, heterophily ratio, and positive rate. Training stages read this file instead of rediscovering graph variants on disk.

The v3 graph stage also writes `variant_audit.csv`. This file is the reproducibility companion to `graph_variants.csv`. It records requested and realized perturbation changes, before/after graph statistics, oracle status, graph view mode, and scenario-specific metrics. This is the file that lets you justify what a severity value actually did.

The result run key is defined in `benchmark/results.py` as `(dataset_id, split_id, scenario_id, severity, graph_seed, training_seed, model_id, protocol)`. This key is used for resumability. If a row with that key already exists in `results.csv`, the training stage can skip it by default. The `--retry-errors` flag changes that behavior so runs with only `status=error` can be attempted again.

The benchmark's reproducibility story depends on several layers working together. The config freezes experiment design. The split seed freezes train/validation/test masks. The graph seed freezes perturbation realizations. The training seed freezes model randomness as much as practical in the PyTorch and DGL stack. The output directory stores a copy of the config and every result row includes identifiers that link back to a graph variant.

When explaining this project, it is worth emphasizing that reproducibility is not just "we set a seed." The implementation separates randomness sources, caches generated graphs, records run keys, writes metadata files, validates configs, and keeps a unified result schema. Those choices make the benchmark easier to audit and rerun.
