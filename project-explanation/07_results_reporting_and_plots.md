# Results, Reporting, And Plots

The reporting system is built around traceability. A report should be able to connect a plotted number back to a model run, a graph variant, a config, and a perturbation audit. That is why the benchmark writes multiple CSV files instead of only saving final figures. Each file has a different role in the evidence chain.

The first important artifact is `graph_variants.csv`. This file is written by the graph stage and acts as the graph ledger. It tells later stages which graph variants exist, which dataset and split they belong to, which scenario and severity produced them, which graph seed was used, whether the scenario used oracle labels, whether the scenario was actually applied, and where the graph binary is stored. It also includes basic graph statistics such as node count, edge count, degree summaries, heterophily ratio, and positive rate.

The second important artifact is `variant_audit.csv`. This file explains what each scenario actually did. For example, it can record selected and actual rewired edge counts, heterophily before and after, changed node counts, cosine similarity shifts under feature camouflage, fraud-to-normal neighbor ratio shifts under relation camouflage, and added edge counts under noise. This is the file that prevents the report from relying on raw severity alone.

The third important artifact is `results.csv`. This is the unified run-level performance table. Every model writes rows into the same schema. Each row includes identifiers, the run protocol, model ID, graph seed, training seed, scenario, severity, metrics, threshold, duration, graph stats, graph paths, train graph reference, status, and error. If a model run fails, the row is still recorded with `status=error` and a truncated error message. This makes incompleteness visible rather than silent.

The run key in `results.csv` is `(dataset_id, split_id, scenario_id, severity, graph_seed, training_seed, model_id, protocol)`. This key is used for resumability and completeness checking. It also explains why the protocol column is part of the key. The same model, seed, and graph variant under `train_on_variant` does not mean the same thing as under `train_clean_eval_all`, so those rows must be distinguishable.

Each training stage writes a stage-specific summary. Baselines write `results_summary_baselines.csv`, PMP writes `results_summary_pmp.csv`, SEC-GFD writes `results_summary_secgfd.csv`, and the shift stage writes `results_summary_shift.csv`. These summary files aggregate successful result rows across training seeds for each graph state and model. They are useful for quick inspection, but the most complete source of truth remains `results.csv`.

The plots stage is implemented in `benchmark/plots_stage.py`. It reads `results.csv`, `graph_variants.csv`, and `variant_audit.csv`. It checks that audit rows exist for graph variants. It computes performance summary curves, clean-to-max-stress drops, robustness scores, audit curves, cross-split summaries, and a joined performance-audit table. It also writes PNG figures under protocol-specific folders.

`plots/summary_curves.csv` is the main plot-ready performance table. It has one row per dataset, split, scenario, severity, model, protocol, and metric. It includes mean, standard deviation, optional confidence interval bounds, run count, oracle status, and whether the point came from the clean graph or scenario rows. The clean point is repeated per scenario because each scenario curve needs its own clean anchor.

`plots/performance_drop_max_stress.csv` compares clean performance with maximum configured severity for each scenario. It is useful when you want a compact table that says how much each model lost under the strongest stress. The drop is computed as clean mean minus stressed mean. Positive drops mean the model performed worse under stress. Negative drops mean the stressed mean was higher, which can happen due to noise or training variance.

`plots/robustness_scores.csv` summarizes an entire severity curve with an area-under-curve style score. The code computes the trapezoidal area over severity and also reports an average metric over the severity range. This is useful when a single max-stress point is too narrow and you want a curve-level robustness summary. It should still be interpreted within a scenario family because severity values are not cross-family calibrated.

`plots/audit_curves.csv` performs the same kind of aggregation for perturbation evidence instead of model performance. It can show how realized heterophily, changed node counts, cosine similarity, or added edges scale with severity. This file is important because it lets the report show that the stress scenario actually changed the graph or features in the intended direction.

`plots/performance_audit_join.csv` joins row-level performance with audit evidence. It includes model metrics together with fields such as oracle status, graph view mode, scenario method, requested change, realized change, and selected audit metrics. This is the best single file when writing a report paragraph that connects performance degradation to realized perturbation strength.

`plots/missing_or_error_runs.csv` is a completeness diagnostic. The plots stage computes expected run keys from the selected variants, configured training seeds, configured models, and protocols present in the results. It then writes any missing or unresolved error runs. This prevents the user from accidentally making figures from incomplete results without noticing.

When the `--ci` flag is used, the plots stage computes bootstrap 95 percent confidence intervals for means, drops, and robustness scores. The implementation uses 1000 bootstrap resamples with a fixed seed. These intervals are useful for visualization and reporting, but they should not be overinterpreted when the number of seeds or splits is small.

The current generated v3 shift run under `runs/gfd_robustness_benchmark_v3/` is a useful example. It has 31 rows in `graph_variants.csv`, 31 rows in `variant_audit.csv`, and 252 rows in `results.csv`. That shape reflects one clean graph, five scenarios, three severities per scenario, two graph seeds, three training seeds, four models, and the clean-train shift protocol. The exact count of evaluated graph states is smaller than the full ledger because severity-zero scenario rows are no-op anchors and the results use one explicit clean state.

The correct reporting habit is to read performance and audit evidence together. If a model drops under `heterophily_rewire_oracle`, check `variant_audit.csv` or `audit_curves.csv` to confirm that heterophily actually increased. If relation camouflage shows little performance change, check whether fraud-to-normal neighbor ratio shifted enough to support a strong claim. If random edge noise has mild effect, check how many edges were actually added and whether heterophily changed.

The final report should keep protocol and oracle status visible in every table or figure that interprets results. A curve under `train_on_variant` tells a different story than a curve under `train_clean_eval_all`. An oracle scenario tells a controlled stress story, not a realistic attack story. The reporting layer was built to keep those distinctions in the CSVs and figure paths, so the explanation should preserve them.
