# Repository And Runtime Pipeline

The repository is organized around one central package, `benchmark/`, and a set of frozen experiment definitions in `configs/`. The `benchmark/` package contains the runner, data loading helpers, perturbation code, model training stages, result schema utilities, and plotting logic. The `Repos/` directory contains vendored research implementations for models such as PMP and SEC-GFD. The benchmark does not rewrite those research repositories into its own style. Instead, it uses thin adapter stages that import the needed model classes and make them fit the benchmark's data, metrics, and output schema.

The main entry point is `benchmark/run.py`. When you run a command such as `py -m benchmark.run --config configs/exp_yelpchi_v3.json --stage graphs`, Python executes the `main()` function in that file. The runner parses CLI flags, loads the JSON config, validates it through `benchmark/config.py`, creates the output directory, and dispatches to the requested stage. This design makes the CLI the stable operational interface while keeping the implementation split into smaller modules.

The first important stage is `graphs`. It is implemented by `_graphs_only()` in `benchmark/run.py`. This stage loads the source dataset, creates deterministic masks, converts the graph into the canonical evaluation view, saves the clean graph, applies each configured perturbation, saves each graph variant, and writes the graph ledger files. The reason this stage exists separately is that graph generation can be expensive and should not be repeated every time a model is trained. By caching graphs once, every model is evaluated on the exact same variants.

The graph stage writes `config.json`, `graph_variants.csv`, `variant_audit.csv`, and graph binaries under `runs/<experiment_name>/graphs/`. The config copy matters because it freezes the exact experiment definition used for that output directory. The graph variant CSV matters because model stages should not recompute which graphs exist. They simply read the ledger, load graph files, and append result rows.

The baseline stage is implemented in `benchmark/baselines_stage.py`. It supports `mlp` and `sage`. For each selected variant and training seed, it loads the cached graph, trains the requested baseline model, evaluates it, and appends a row to `results.csv`. It also writes `results_summary_baselines.csv`, which aggregates completed rows across training seeds. The baseline code is important because it provides sanity references for the specialized research models.

The PMP stage is implemented in `benchmark/pmp_stage.py`. It reads the benchmark config, loads the PMP YAML settings from `Repos/PMP-master/config/`, merges benchmark-side overrides, creates DGL dataloaders, trains LA-SAGE-S, and writes results in the same schema as the baselines. This adapter stage exists because the original PMP repository has its own training script and assumptions. The benchmark needs PMP to run inside the unified matrix so it can share splits, graph variants, metrics, and result files.

The SEC-GFD stage is implemented in `benchmark/secgfd_stage.py`. It imports the SEC-GFD model class from `Repos/SEC-GFD-main/model/SECGFD.py`, resolves hyperparameters from config and CLI overrides, trains the model on a cached graph, and evaluates test metrics. It also includes benchmark-side fixes and adaptations, such as caching spectral theta coefficients and using validation monitoring rather than relying on the original repository's script behavior.

The `matrix` stage in `benchmark/matrix_stage.py` is a launcher. Under the standard `train_on_variant` protocol, it runs the baseline stage, PMP stage, and SEC-GFD stage in sequence, depending on which models are configured or selected through `--models`. Under the `train_clean_eval_all` protocol, it dispatches to the shift stage instead. This means `matrix` is not a new model implementation. It is an orchestration convenience for running the integrated model set.

The `shift` stage in `benchmark/shift_stage.py` implements the clean-train protocol. For each dataset and split, it finds the clean graph, trains each selected model once per training seed on that clean graph, and then evaluates the trained artifact on every selected variant. This is why shift rows include `train_graph_ref`: it records that the model was trained on the clean graph even when the evaluation row refers to a stressed graph. This column is essential for interpreting distribution-shift results.

The `plots` stage in `benchmark/plots_stage.py` is the reporting layer. It reads `results.csv`, `graph_variants.csv`, and `variant_audit.csv`, checks for missing or error runs, builds summary CSVs, computes optional bootstrap confidence intervals, joins performance with audit evidence, and writes PNG figures. This stage does not train models or generate graphs. Its job is to transform raw run-level outputs into report-ready artifacts.

The pipeline is intentionally staged. In a single end-to-end run, the order is graph generation first, model evaluation second, plotting third. That separation gives the project reproducibility and resumability. If model training crashes halfway through, the cached graph variants remain available. If plots need to be regenerated with confidence intervals, the benchmark can reuse existing results. If one expensive model is missing, the `--models` flag can fill only that part of the matrix.

The output directory is usually `runs/<experiment_name>/`, where `experiment_name` comes from the config. This convention keeps v1, v2, v3, fast, and full experiments separate. The repository treats `configs/*.json` as frozen definitions. If the design changes, the intended workflow is to add a new config rather than silently editing an old one. That is why the repo contains multiple config versions.
