# Plain English Overview

This project is a controlled testing lab for fraud detection models that use graphs. A graph is a way to represent entities and relationships. In a fraud dataset, a node can represent an account, user, review, or transaction-like entity, and an edge represents some relationship between two nodes. The model's task is to decide which nodes are fraudulent or anomalous. The project uses YelpChi through DGL's `FraudDataset`, which gives the benchmark a real fraud graph with node features, labels, and relations.

The basic motivation is that fraud detection is not only about doing well on one clean dataset. Real fraud graphs can become messy. Fraudulent nodes may connect to normal-looking nodes, fraudsters may make their attributes look normal, and graph neighborhoods may become crowded with irrelevant relationships. A model that performs well on the original graph may fail when those stresses are introduced. This benchmark exists to make that question measurable.

The benchmark does not try to simulate a real fraudster end to end. Instead, it creates controlled stress tests. That difference matters. A realistic simulator would need time, attacker strategies, business rules, feedback loops, and changing behavior. This repository does something narrower and more practical for a course project: it takes a fixed graph and applies clear, repeatable changes to it. Then it checks how model performance changes.

The main idea is to create multiple versions of the same graph. One version is clean, meaning it is the original graph after the benchmark has applied a fixed data split and converted it into the chosen evaluation format. Other versions are stressed variants. For example, one variant may rewire edges so that nodes connect more often to opposite-label nodes. Another variant may change fraud-node features so they look like normal-node features. Another may add random edges to make neighborhoods noisier.

The project then evaluates several models on those graph variants. The simplest model is `mlp`, which reads node features but ignores edges. That model is important because it acts as a sanity check. If only the graph edges change, the MLP should not change much under the clean-train shift protocol because it does not use the graph structure. The `sage` model is a standard GraphSAGE baseline that does use message passing over edges. The `pmp` and `secgfd` models are specialized graph fraud detection methods imported from vendored research repositories under `Repos/`.

The benchmark measures three main metrics. ROC-AUC measures how well the model ranks fraud nodes above normal nodes without needing one fixed threshold. Average precision is useful when fraud is rare, because it focuses on the quality of high-scoring positive predictions. Macro-F1 uses hard predictions and balances the fraud and normal classes, but it needs a threshold. The implementation chooses that threshold using validation data, not test data, because choosing it on test data would leak information and make results look better than they really are.

There are two evaluation protocols. In `train_on_variant`, the model is trained separately on each stressed graph and evaluated on that same stressed graph. This answers how well a model can adapt when it sees the same type of stress during training. In `train_clean_eval_all`, the model is trained once on the clean graph and then evaluated on all graph variants. This answers how much performance is lost when the model was trained under normal conditions but tested under stress. These protocols answer different questions, so their results should not be averaged together.

The output of the project is designed to be traceable. `graph_variants.csv` tells you which graph variants exist and where their cached graph files are stored. `variant_audit.csv` tells you what each stress scenario actually did, such as how many edges were rewired or how much feature similarity changed. `results.csv` records the model performance for each exact run. The plots stage then turns those files into summary CSVs and PNG figures that can be used in a report.

The most important communication point is that raw severity is not enough. A severity value such as `0.3` means different things in different scenarios. In one scenario it may mean rewiring 30 percent of eligible edges. In another it may mean selecting 30 percent of fraud nodes for feature camouflage. Those are not directly comparable. The benchmark therefore writes audit files so the report can say what was actually changed, not only what was requested.

If you need to explain the project in one sentence, say this: the repository builds a reproducible static robustness benchmark for graph-based fraud detection by creating controlled stressed versions of YelpChi, evaluating multiple models under clear protocols, and exporting both performance results and perturbation audits.
