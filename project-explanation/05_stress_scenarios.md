# Stress Scenarios

The stress scenarios are the core of the benchmark. They are implemented in `benchmark/scenarios.py`, with relation-aware helper functions in `benchmark/relation_utils.py` and tabular audit export in `benchmark/scenario_audit.py`. A scenario is a deterministic transformation of a graph or its node features. The benchmark applies scenarios to create graph variants, then evaluates models on those variants.

Every scenario is described by a `ScenarioSpec`. This object contains the scenario ID, family, method name, oracle-label flag, severity parameter name, severity value, graph seed, and scenario parameters. The dispatcher `apply_scenario()` reads this spec and calls the implementation for the requested method. This design lets configs declare scenarios without hard-coding experiment logic into the runner.

The random number generator is deterministic per scenario spec. The helper `_rng_for_spec()` builds a stable seed from the scenario ID, method, graph seed, severity, and sorted scenario parameters. It hashes that text into a 32-bit seed. This means the same scenario with the same graph seed and parameters should produce the same variant, even across process restarts. It also means changing the severity or method changes the random stream in a controlled way.

The implementation protects the supervised task definition. After an applied perturbation, `_assert_invariants()` checks that the node count did not change, labels did not change, train/validation/test masks did not change, and the feature tensor shape did not change. This matters because the benchmark is supposed to stress the graph or features while keeping the classification task comparable. If a scenario changed labels or split masks, results would no longer be comparable to the clean graph.

Several scenarios sample or rewire edges. They share an `EdgeSamplingPolicy` from `benchmark/relation_utils.py`. The v3 configs usually disallow self-loops, reject already-existing edges, reject duplicate sampled edges, and use a bounded attempt budget. This policy is important because requested changes can differ from realized changes. If many candidate edges are invalid, the scenario records that through rejection counters and realized-change fields.

Heterophily stress tests whether message passing remains useful when neighbors become less label-consistent. A graph is homophilic when connected nodes often share the same label. A graph is heterophilic when connected nodes often have different labels. Standard GNN aggregation can struggle under heterophily because a node's neighborhood may send misleading class signals. The benchmark measures heterophily with the ratio of edges whose source and destination labels differ.

The oracle heterophily scenario is `heterophily_rewire_oracle`. It uses true labels to choose opposite-label destinations. The code selects a severity-controlled fraction of eligible edges, keeps each selected edge's source node fixed, and tries to replace the destination with a node from the opposite label class. It rebuilds the graph with the modified edge list and records how many edges were selected, how many actually changed, and how the heterophily ratio moved. This is a strong controlled stress, but it is oracle-based and must be disclosed.

The non-oracle heterophily scenario is `heterophily_rewire_nonoracle`. It avoids true labels during target selection by first assigning nodes into two feature-derived pseudo groups with a simple two-means procedure. Then it rewires edges toward the opposite pseudo group. True labels are still used for auditing the before/after heterophily ratio, but not for construction. This scenario is useful because it gives a non-oracle reference, although its realized label heterophily may be much weaker than the oracle version.

Feature camouflage is implemented as `camouflage_feature_oracle`. The idea is that fraud nodes may disguise their attributes to look like normal nodes. The code selects a severity-controlled fraction of fraud nodes, samples normal nodes, and replaces or blends each selected fraud feature vector with a sampled normal feature vector. In the current v3 configs, `gamma = 1.0`, which means full replacement. The audit records how many nodes changed, the mean L2 feature delta, and cosine similarity to sampled normal features before and after.

Feature camouflage is valuable because it directly tests feature dependence. If all models consume node features, then strong feature camouflage should affect all of them. It is also a useful sanity check for the MLP. Since MLP ignores edges, graph-only perturbations should not affect it under clean-train shift, but feature camouflage can affect it because the features themselves have changed.

Relation camouflage is implemented as `camouflage_relation_oracle`. The idea is that fraud nodes may hide by connecting to normal-looking neighbors or by reducing suspicious fraud-to-fraud structure. The code selects a severity-controlled fraction of fraud nodes, adds a configured number of edges from each selected fraud node to sampled normal nodes on selected relations, and optionally removes a fraction of suspicious edges from selected fraud nodes to fraud nodes. The current v3 configs use `camouflage_edges_per_node = 2` and `remove_suspicious_ratio = 0.5`.

Relation camouflage is relation-aware in v3. The config can set `graph_view_mode` to `heterograph_aware_generation`, which causes the graph stage to pass the source heterograph into `apply_scenario()` and then convert the perturbed result back to the homogeneous canonical view. This preserves relation semantics during generation while keeping one evaluation interface. The audit records neighbor composition, including fraud-to-normal and fraud-to-fraud neighbor ratios before and after.

Random edge noise is implemented as `noise_edges_uniform`. It adds uniformly sampled edges to selected relations. The severity controls the requested number of edge pairs relative to the eligible edge count. The policy rejects self-loops, existing edges, and duplicates by default. If `undirected` is true, the code can also add mirrored edges, but the current v3 configs use directed additions. This scenario tests density and neighborhood clutter rather than a targeted fraud strategy.

The code treats severity `0.0` as a no-op. `apply_scenario()` returns the original graph, marks `scenario_applied` as false, and records the reason as `severity==0`. The graph stage stores these no-op rows as references to the clean graph. This is useful because each scenario curve needs a clean anchor point, but the project does not need to duplicate graph binaries for identical graphs.

The graph view mode is a key v3 detail. A scenario with `graph_view_mode = canonical` edits the canonical evaluation graph directly. Feature camouflage uses this because it only changes node features and does not depend on relation types. A scenario with `graph_view_mode = heterograph_aware_generation` edits the source heterograph before homogenization. Heterophily rewiring, relation camouflage, and noise use this mode in v3 so relation filters such as `net_rsr`, `net_rtr`, and `net_rur` can be honored.

The most important way to explain scenarios is through the trio of what, why, and how. What: the scenario creates a controlled graph or feature stress. Why: it targets a known weakness of graph fraud detection, such as misleading neighbors or disguised attributes. How: the code applies deterministic, seed-controlled transformations and writes audit metrics so the claimed stress can be verified.
