# Methodology And Research Design

The research question behind this repository is: when a fraud graph becomes structurally or feature-wise less reliable, which graph-based fraud detection models degrade the most, and under what kind of stress? This is a robustness question rather than a pure accuracy question. A normal benchmark might train models on a dataset and report the best score. This project instead asks how scores move as the graph is deliberately changed.

The supervised learning task is binary node classification. Each node has features and a label, where label `1` represents the fraud or anomalous class and label `0` represents the normal class. The model predicts a fraud probability or score for each node. The graph matters because graph neural networks do not only look at a node's own features. They also aggregate information from neighbors. That aggregation is useful when neighbors carry helpful signal, but it can become harmful when neighborhoods are noisy, heterophilic, or camouflaged.

The dataset choice is YelpChi through `dgl.data.FraudDataset`. This choice is practical because the vendored fraud detection methods in `Repos/` are graph-oriented and YelpChi is a common graph fraud detection benchmark. The benchmark code uses DGL as the common graph representation because DGL gives a consistent way to load the dataset, manipulate graphs, save graph binaries, and run graph neural network layers.

The benchmark fixes train, validation, and test masks before generating graph variants. This is important because the goal is to compare models and perturbations, not to introduce accidental variation from changing splits. If the clean graph and stressed graph used different test nodes, then a performance difference could be caused by the split rather than the stress scenario. The implementation overwrites masks in `benchmark/data.py` with deterministic stratified masks based on the configured `split_seed`.

The design separates graph seeds from training seeds. A graph seed controls the random choices inside perturbations, such as which edges are rewired or which fraud nodes are camouflaged. A training seed controls model initialization, optimization randomness, and dataloader sampling. This separation matters because it lets the benchmark distinguish two kinds of variance. If results vary across graph seeds, the exact perturbation realization matters. If results vary across training seeds, the model training process is unstable.

The benchmark uses stress scenarios because robustness needs a controlled independent variable. The main scenario families are heterophily, camouflage, and noise. Heterophily stress makes edges connect more often across labels, which challenges message passing methods that expect neighborhoods to be informative. Feature camouflage makes fraud-node features look more normal, which challenges feature-based discrimination. Relation camouflage changes fraud-node neighborhoods so they look more benign. Random edge noise increases graph clutter and density.

The current v3 configs make an important distinction between oracle and non-oracle scenarios. An oracle scenario uses true labels to construct the perturbation. For example, oracle heterophily rewiring uses labels to choose an opposite-label destination. This is acceptable in a controlled benchmark because the goal is to create a strong and interpretable stress, but it must be disclosed. A non-oracle scenario avoids true labels during construction. The non-oracle heterophily scenario uses a simple feature-derived two-means partition instead of labels, and random noise does not use labels.

The severity value is a scenario-specific control knob. In heterophily rewiring, severity controls the requested fraction of eligible edges selected for rewiring. In feature camouflage, severity controls the fraction of fraud nodes selected for feature replacement or blending. In relation camouflage, severity controls the fraction of fraud nodes whose outgoing neighborhood is modified. In random edge noise, severity controls how many edge pairs are requested relative to the existing edge count. Because these meanings differ, severity should mainly be compared within one scenario family.

The benchmark uses two protocols because "robustness" can mean two different things. The `train_on_variant` protocol trains and evaluates on the same graph variant. This is closer to asking whether a model can learn under stressed conditions if the training data already reflects that stress. The `train_clean_eval_all` protocol trains on the clean graph and evaluates on stressed variants. This is closer to asking whether a model trained in normal conditions is stable under test-time shift. Both protocols are useful, but they answer different questions.

The metrics are selected for imbalanced fraud classification. ROC-AUC is threshold-free and measures ranking quality. Average precision is also ranking-based and is especially informative when the positive class is rare. Macro-F1 is threshold-sensitive but useful because it treats both classes with equal importance. The implementation chooses the F1 threshold on validation predictions and then applies it to test predictions. This avoids test leakage and makes the reported F1 more defensible.

The benchmark evaluates four model types in the main configs. The MLP baseline reads features only, so it tells you how much can be done without graph structure. GraphSAGE is a standard message passing baseline, so it provides a simple graph-neural reference point. PMP is a specialized model designed for graph fraud detection with label imbalance and heterophily concerns. SEC-GFD is another specialized model built around spectral filtering and local constraints for heterophilic fraud graphs. Comparing simple baselines with specialized methods makes the robustness story more meaningful.

The final reporting design keeps performance and perturbation evidence separate but joinable. `results.csv` records performance. `variant_audit.csv` records what the stress did. `plots/performance_audit_join.csv` joins them for report use. This is a strong design choice because it prevents the report from interpreting a performance drop without checking whether the perturbation actually had the intended effect.

The main limitation is that this is a static synthetic stress benchmark. It does not simulate time, adaptive attackers, production fraud review systems, or retraining feedback. It also uses one primary dataset in the provided configs. These limitations do not invalidate the project, but they define the correct scope of claims. The safe claim is comparative robustness under controlled graph stress, not real-world production readiness.
