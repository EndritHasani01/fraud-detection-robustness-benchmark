# Tests And Quality Controls

The test suite under `tests/` is designed to protect benchmark behavior rather than to prove that every full deep learning experiment will run in the current machine environment. Many tests use mocked stages or small fake graph classes so they can verify semantics quickly without downloading YelpChi or training large models. This is a practical choice because the full benchmark depends on DGL, PyTorch, and vendored research code, which can be slow and environment-sensitive.

Config tests verify that frozen experiment definitions remain valid and intentional. `tests/test_config.py` checks the validation logic for seeds, SEC-GFD hyperparameters, v3 scenario metadata, oracle-mode conflicts, graph view modes, relation filters, relation camouflage parameters, and audit export controls. `tests/test_config_files.py` loads the frozen configs and checks important expected values, such as v3 scenario IDs, severity grids, graph seeds, training seeds, model lists, and audit metrics.

Scenario tests are especially important because the stress transformations define the benchmark's meaning. `tests/test_scenarios.py` uses fake homogeneous and heterograph classes to test the scenario dispatcher without requiring DGL. The tests check that zero severity is a no-op, oracle rewiring increases heterophily and preserves protected node data, blocked rewiring logs selected versus realized counts, non-oracle rewiring is deterministic for the same seed, feature camouflage changes only fraud nodes and increases similarity to sampled normal nodes, relation camouflage changes neighbor mix and edge count, and noise rejects existing edges, duplicates, and self-loops under the default policy.

The scenario tests also protect a subtle but important design point: labels and split masks should not change. Helper assertions verify that `label`, `train_mask`, `val_mask`, and `test_mask` remain equal after perturbations. This matters because if a perturbation changed the supervised task definition, the benchmark would no longer be measuring model robustness on the same classification problem.

Scenario audit tests in `tests/test_scenario_audit.py` verify that nested scenario logs become consistent CSV rows. They check that requested and realized metrics are normalized, non-applicable metrics are left blank, no-op scenarios default to zero realized change, and CSV header/append behavior works. These tests matter because audit files are central to the report's credibility.

Result and resumability tests in `tests/test_results.py` protect the unified result schema. They check that old result headers can be migrated, completed-key loading respects the `--retry-errors` behavior, result rows are built consistently from variant rows, baseline stages skip completed rows before loading graphs, and error rows can be retried. This is operationally important because long benchmark runs should not restart from scratch after interruption.

Operational tests in `tests/test_operational.py` check CLI and stage behavior. They verify that `--models` is passed to stages, that the `--ci` flag reaches the plots stage, that interrupted runs report the correct status, that graph-stage temporary manifests are cleaned up on failure, that heterograph-aware generation passes the source graph into scenario code, and that matrix dispatch respects model filters. These are not mathematical tests, but they protect the workflow users actually run.

PMP and SEC-GFD tests protect the adapter layers around vendored research code. `tests/test_pmp_stage.py` checks that PMP YAML config is shallow-merged with benchmark hparams, that worker count is platform-aware, and that shift stage uses resolved PMP config. `tests/test_secgfd_stage.py` checks theta caching, config hparam resolution, CLI override precedence, and runner forwarding of SEC-GFD override flags. These tests are important because adapter bugs can silently make the benchmark run a different model configuration than intended.

Shift-stage tests in `tests/test_shift_stage.py` verify that the clean-train protocol trains once and evaluates all variants, that `matrix --protocol train_clean_eval_all` dispatches to the shift stage rather than standard per-variant training, and that completeness reporting understands shift protocol rows. This protects the meaning of `train_clean_eval_all`.

Plot-stage tests in `tests/test_plots_stage.py` verify reporting behavior. They check that oracle and cross-split summaries are written, that completeness summaries are printed, that audit rows are joined by key and per protocol, and that missing audit files or audit rows fail clearly. These tests matter because plots can look authoritative even when data is incomplete. The code is designed to fail loudly in those cases.

The test suite has limits. It does not guarantee that the full YelpChi DGL dataset will download in the current environment. It does not guarantee that every CUDA or CPU dependency combination is installed correctly. It does not prove that every generated plot supports a strong research conclusion. It also does not replace manual review of `variant_audit.csv` and `missing_or_error_runs.csv` before using results in a report.

The strongest quality-control story is that the repo tests the contract around reproducibility, scenario semantics, result schema, resumability, protocol separation, and reporting diagnostics. Those are the parts most likely to create misleading benchmark claims if they break. Full experimental correctness still requires running the graph stage, checking audit outputs, checking missing or error runs, and interpreting results within the benchmark's stated limits.
